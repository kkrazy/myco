## 一、目标与最终结论（先看这里）

难题总结.md §4 要求：4KB 块独立压缩、比率损失 <5% vs LZ4、任意块不膨胀、
鲲鹏 920 单核压缩 >1 GB/s、解压 >5 GB/s、Silesia 验证后鸿蒙镜像验证。

**最终结果（Silesia 全集 212MB，10/10 复测）**：

| 要求 | 结果 | 判定 |
|---|---|---|
| 4KB 块独立压缩 | MC4K 容器逐块独立，块间零依赖 | ✅ |
| 损失 <5% vs LZ4（1.733） | **1.649**（损失 4.9%） | ✅ |
| 任意块不膨胀 | 压不动则存 raw，selftest 逐块检查 0 膨胀 | ✅ |
| 单核压缩 >1 GB/s | 单线程 0.72 ❌ / 双 SMT 线程 **1.044** ✅ | ⚠️ 口径① |
| 单核解压 >5 GB/s | 单线程 4.10 ❌ / 双 SMT 线程 **5.06–5.12** ✅ | ⚠️ 口径① |
| Silesia 验证 | 已做 ✅ | |
| 鸿蒙 6.1 镜像验证 | **未做（本环境无镜像数据）** | ❌ 待办 |

**三个需需求方裁决的口径问题（详见附录 B）**：
1. **"单核"定义**：v5-mt 用一个物理核的两个 SMT 线程（鲲鹏 920 官方设计，
   OS 调度器视作 2 核）。按"物理核"口径双达标；按"单线程"口径未达标且
   已证明无已知路径（12+ 实验族到墙）。
2. **主频口径**：需求上限 2.6GHz，本机实测 2.88GHz。严格按 2.6GHz 折算
   v5-mt 为 c ≈0.94 / d ≈4.60，**两项都不达标**（差 6–8%）。
3. **需求内部矛盾**：LZ4 基线自身 Silesia 全集仅 1.733 < 2:1，"损失 <5%"
   与"Silesia >2:1"（若指全集）不可能同时满足；单文件口径下 xml 2.70 /
   samba 2.01 / nci 3.72 等 >2:1 ✅。

## 二、迭代史（每轮：方法 → 目标 → 结果）

分类标记：**【算法】**= 改变压缩/解压的数据结构或决策逻辑（编码调度、
哈希、匹配策略、并行分块）；**【工程】**= 不改算法语义的实现层优化
（编译选项、内存复用、线程编排、容器布局、测量方法）。一轮内可两者
皆有，按主要贡献标注。

基线：LZ4 v1.10.1，4KB 独立分块 level 1，本机单线程实测
**ratio 1.733 ｜ c 0.477 GB/s ｜ d 2.97 GB/s**。

### 第 1 轮（v2，自研编码器起步）【算法】
- **方法**：替换 v1 自研编码器核心（skip 调度扫频）。
- **目标**：压缩比损失从 v1 的 4.1% 收窄。
- **结果**：ratio 1.700（损失 1.9%，✅ 减半），但 c 0.306 仅为基线 59%。
  自研路线起点 ratio 好但速度差太远。

### 第 2 轮（v3，自研解码器重构）【算法为主，工程为辅】
- **方法**【算法】：编码调度重扫 + 自研解码器重构（NEON match 拷贝）+
  SVE 批量探测实验（工程量最大，**否决**：SVE 逐 lane gather 打断向量流水）。
- **目标**：解压提速、压缩换速度。
- **结果**：c 0.339（+11%）、d 2.45（+14%）、ratio 1.681（3.0%）。方向对但
  自研路线离目标数量级仍远。

### 第 3 轮（v4，策略转向：直接改造 LZ4 内核）【算法】
- **方法**：放弃自研，vendor 上游 lz4.c 内核，扫参数（SKIP_TRIGGER /
  acceleration），消耗 5% 比率预算换速度。
- **目标**：把 c 拉近基线以上。
- **结果**：**c 0.634（+33% vs 基线）**、d 3.24、ratio 1.654。转向成功，
  单核框架确立。

### 第 4–5 轮（v4.1/v4.2，编译层与调度微调）【工程】
- **方法**：块间 stream 复用（免 per-block 16KB memset）；PGO 两遍 + LTO。
- **目标**：免算法改动的确定性提速。
- **结果**：v4.1 c 0.638；v4.2 **c 0.658（+38%）、d 3.59（+21%）**，PGO
  单独贡献解压 +9%。

### 第 6 轮（v4.3，内核手术）【算法】
- **方法**：强制 byU32+hash5 小块路径（5 字节指纹预筛候选）、
  SEARCH_INIT_SHIFT 早期探测加密。
- **目标**：压缩再上台阶。
- **结果**：**c 0.718（+51% vs 基线）、d 4.10（+38%）**，ratio 1.651 不变。

### 第 7–8 轮（v4.3 确认 / v4.4，自适应调度 + 扫尾）【算法为主，工程为辅】
- **方法**【算法】：块自适应 acceleration（按上一块压缩率调探测密度）；
  【工程】hash 素数/表宽/编译层剩余扫描（全部无增益，收敛证据）。
- **结果**：**v4.4 定版：ratio 1.649（4.9%）、c 0.721、d 4.12**。单线程
  累计 ×1.51 / ×1.39，距 1.0/5.0 各差 28%/18%（2.88GHz 口径）。

### 第 9 轮（压缩专项，~20 个实验全部否决）【算法 × 工程，均到墙】
- **方法**【算法】：x2rotate 哈希、双探测候选、派生长匹配、静态/自适应
  早退、全表重置、运行时触发器；【工程】-O2/分编译、双流交错、容器消开销。
- **目标**：单线程压缩跨 1.0 线。
- **结果**：**零采纳**。结构性归因：0.62 探测/字节 vs 更优哈希 0.32——
  "更好候选"的收益被更高探测指令成本吃光；容器开销仅 0.5%。
  **单线程框架墙确认**。

### 第 9.5 轮（CPU 鉴定与重大更正，见附录 A）【工程（测量方法）】
- 更正了第 8–9 轮基于的两个错误假设：本机不是"2.0GHz 降速 VM 核不可信"，
  而就是鲲鹏 920 @2.88GHz 真机（此前所有"2.6GHz 外推可能过线"的乐观
  结论作废，缺口是真实的）。

### 第 10 轮（v5-mt，双 SMT 线程路线 —— 达标轮）【工程（并行化）】
- **前置实测**【工程】：两个进程各钉一个 SMT 兄弟线程，物理核墙钟聚合
  c 1.105 / d 5.87 GB/s——**一个物理核的算力本身就够两个目标**，
  无需改压缩算法。
- **方法**【工程】：持久线程池 + 交替块条带；解压端流水线（leader 边走
  块头边解、follower 拼 atomic cursor，藏掉 3.2% 串行前缀）；补上 PGO
  （注意坑：并发 gcda 需 `-fprofile-update=atomic`；训练必须传文件列表，
  目录参数会让 profile 失真导致 PGO 产出 7 倍慢的代码）。
  【算法】唯一改动：块→线程的分配策略（奇偶条带，块本身仍独立压缩，
  输出格式不变）。
- **试错**【工程】：自旋等待池污染同进程 CPU 时间账（回退 mutex 池）；
  1:2 分工比 1:1 更差（回退）；两端相向填充省拷贝无增益（回退全量紧凑）。
- **目标**：单物理核口径下 c >1.0、d >5.0。
- **结果**（SMT 兄弟绑核，10/10 全过）：
  **c 1.042–1.047 ✅ ｜ d 5.062–5.123 ✅ ｜ ratio 1.649 不变 ｜
  selftest（10000 fuzz + 500 轮池复用压测）✅ ｜ 块膨胀 0 ✅**。
  附：不绑核（两个物理核，非单核口径）c 1.29 / d 6.1。
  NEON 解码器在真硬件重测维持否决（−20% vs 标量）。

### 累计曲线

| 版本 | 类型 | ratio（损失） | c GB/s | d GB/s |
|---|---|---|---|---|
| LZ4 基线 | — | 1.733 | 0.477 | 2.97 |
| v3（自研顶点） | 算法 | 1.681（3.0%） | 0.339 | 2.45 |
| v4.2（PGO） | 算法+工程 | 1.651（4.7%） | 0.658 | 3.59 |
| v4.4（单线程定版） | 算法+工程 | 1.649（4.9%） | 0.721 | 4.12 |
| **v5-mt（双 SMT）** | 工程（并行） | **1.649（4.9%）** | **1.044** | **5.09（中位）** |

**两类手段的贡献拆分**（单线程口径，vs 基线 c 0.477 / d 2.97）：
- **算法类**（调度/哈希/自适应，第 3/6/7 轮）：c +33%（0.477→0.634 是
  参数扫频，→0.718 是内核手术），d 间接受益 +9%；ratio 从预算边消耗
  到 4.9%。
- **工程类**（stream 复用/PGO/LTO，第 4–5 轮）：c +5%、**d +21%**
  （PGO 是解压侧最大单笔收益）。
- **工程类**（SMT 并行化，第 10 轮）：c ×1.45、d ×1.24（相对 v4.4），
  把两条单线程墙同时跨过——**达标靠的是工程并行，不是算法突破**；
  算法侧（第 9 轮 ~20 实验）已证明单线程无路径。

## 三、部署注意事项

1. **调用粒度 ≥ MB 批次**：线程编排同步开销 10.4µs/调用，4KB 逐块调用
   场景（单页 ZRAM 路径）应回退单线程 v4.4 路径（0.5µs/调用）。
2. **绑核**：需绑同一物理核的两个 SMT 兄弟（查
   `/sys/devices/system/cpu/cpuN/topology/thread_siblings_list`）。
3. **构建**：`build-v4.sh` 一键出三个产物（v4full / v4 / bench_mt），
   两遍 PGO 已含 atomic 修正与文件列表训练。
4. **格式兼容**：v5-mt 与单线程产物逐字节兼容（同一 MC4K 容器），
   可混合部署、互相解压。

## 附录 A：CPU 鉴定（2026-10-30，更正此前错误结论）

- **MIDR_EL1 = 0x480fd020**：HiSilicon **TaiShan v120**（鲲鹏 920 家族，
  乱序宽发射核；此前误读为 Cortex-A53 类顺序核，导致方向性误判）。
- **实测主频 2.84–2.88 GHz**（asm 依赖链标定）；QEMU 声称 2.0GHz 不准；
  **steal 0.0%**（CPU 时间 vs 墙钟一致，/proc/stat st=0）。
- "三个进程同钉一个 vCPU 各自满速"的真实原因是 **SMT**（2 线程/核，
  相邻 vCPU 号是兄弟超线程），不是"vCPU 浮动"。
- **结论**：本机全部数字即鲲鹏 920 真机数字，无需外推；第 8–9 轮的
  "×1.3 外推"乐观结论作废，缺口真实存在（此判断决定了第 10 轮转向）。

## 附录 B：口径问题明细（需需求方裁决）

1. **"单核" = 物理核（含 2 SMT 线程）还是单线程？**（双 SMT 是否算单核）
   - **支持物理核口径**：(a) 鲲鹏 920 出厂即 SMT2，两条线程共享同一
     物理核的 L1/L2、乱序后端、功耗域，是核内资源而非"多核并行"
     （§三反对的是多核并行的额外开销，SMT 不引入）；(b) **资源上界
     实测**——兄弟线程对 d=5.09，跨物理核对 d=6.1，双 SMT 被单核
     后端封顶，从未超过一个物理核的算力；(c) SMT 增益 c ×1.45 /
     d ×1.24，远低于真双核 ×2，是"利用核内空闲发射槽"的特征；
     (d) ZRAM 生产形态按 per-CPU worker 消费调度器可见 CPU，SMT
     线程天然参与。
   - **支持单线程口径**：(a) SPEC 及需求 §三对比表（"基于单核
     2.6GHz"）的业界数字均为单线程惯例；(b) 云采购口径 1 vCPU =
     1 SMT 线程；(c) §三动机是"提升单核以摆脱多核依赖"，SMT 计入
     有绕过动机之嫌。
   - **结论**：双 SMT 未超出一个物理核的物理资源，物理核口径下成立
     且论据扎实；单线程口径下不算，且单线程目标经 12+ 实验族证明
     软件不可达（LZ4 探测发射墙 + NEON 解码慢 20%），届时只能靠
     硬件加速（§三自述方向）或调整目标。**需需求方书面裁决**。
2. **主频口径**：需求写"最高 2.6GHz"。本机 2.88GHz 实测数字若严格
   折算 2.6GHz：v5-mt c ≈0.94 / d ≈4.60，两项差 6–8% 未达标。若按
   "2.6GHz 级别算力"理解（同代同构核，实际部署频率更高），则达标。
3. **Silesia >2:1 的范围**：全集平均受 LZ4 基线自身 1.733 封顶，
   "损失 <5%" 与 "全集 >2:1" 互斥；单文件口径多个 >2:1 ✅。
   建议确认该条指单文件或指特定数据类型。
